## 2. Что на самом деле в дипломе (грounding-факты, не путать с реконструкцией)

- Специальность — управление качеством/экономика, не CS. Комиссия защиты —
  не ML-инженеры (это уже не актуально, защита прошла, но полезно помнить
  для тона будущих объяснений).
- Реальная компания: ООО «Спецмастер», Республика Коми, микропредприятие,
  обслуживание приборов учёта тепла/воды.
- Реальный пилот: АИС на базе ЛЭРС УЧЁТ, 32 объекта, апрель-май 2026,
  97.8% успешных сессий опроса.
- **Реальные бизнес-результаты пилота (из диплома, использовать только эти
  числа как "реальные", никогда не подменять синтетическими):**
  - Ложные выезды: 6-8/мес → 1-2/мес (↓ ~75%)
  - Пропущенные отказы: 3/квартал → ≤1/квартал
  - Время реакции: 24-72ч → 2-6ч
  - Диплом сам честно пишет об ограничениях: пилот маленький (32 объекта,
    2 месяца), частично ретроспективный, нужна проспективная апробация.
- Сеть — 11 узлов, три яруса:
  - Вход (5): давление, температура, расход, срок поверки, срок эксплуатации
  - Скрытые (3): техническое состояние прибора, состояние трубопровода,
    достоверность показаний
  - Выход (3): вероятность отказа, необходимость ТО, аномальное потребление
- CPT `device_cond` (Табл. 3.3) и `pipe_cond` (Табл. 3.4) — **точно**
  воспроизведены из диплома. Остальные CPT (`reliability`, `failure_prob`,
  `maintenance`, `anomaly`) — **реконструированы мной**, полные таблицы из
  HUGIN `.net` в тексте диплома не опубликованы.
- Диплом сам предлагает pgmpy/pomegranate как открытую замену HUGIN при
  тиражировании системы — то есть Python-репозиторий продолжает логику
  самого диплома, а не привносит чужеродную идею.
- Три готовых диагностических сценария из Табл. 3.6 использованы как
  регрессионные тесты (см. ниже).

## 4. Хронология багов pgmpy и как чинили (важно для будущих правок)

Я (Claude) не могу установить pgmpy в своей песочнице (нет интернета), поэтому
весь pgmpy-код пишется "вслепую" по памяти API и проверяется пользователем
локально (Windows, Python 3.14.6, очень свежая/bleeding-edge версия pgmpy).
Уже пойманы и исправлены:

1. **`BayesianNetwork` → `DiscreteBayesianNetwork`**: в установленной версии
   pgmpy старое имя при импорте кидает ImportError, не просто варнинг.
   Исправлено try/except импортом в `src/network.py`.
2. **Изолированный узел `temperature`**: `BayesianNetwork(EDGES)` создаёт
   узлы только из списка рёбер; `temperature` умышленно ни с чем не связан
   (см. п.2), поэтому падал на `add_cpds` с "CPD defined on variable not in
   the model". Исправлено явным `model.add_node("temperature")`.
3. **Отсутствие `state_names`**: без явного `state_names=` в `TabularCPD`
   pgmpy трактует состояния как int-индексы, evidence строками не резолвится.
   Добавлено во все CPD в `src/network.py`.
4. После этих трёх фиксов: **все 13 тестов (`test_reference.py` +
   `test_network_pgmpy.py`) проходят**, только `FutureWarning` про
   `pgmpy.estimators.StructureScore` → `pgmpy.structure_score` (это
   внутренний варнинг самого pgmpy при импорте пакета, не наш баг, ничего
   чинить не нужно, просто иметь в виду при написании structure learning).
5. Обучение параметров (`src/learning.py`, MLE/BayesianEstimator) — **сработало
   с первого раза** после того как я стал осторожнее с индексацией
   (`try_quantitative_diff`/`max_abs_diff` обёрнуты в try/except, чтобы
   таблицы печатались даже если численный дифф не считается). Результат:
   макс. |learned - expert| = 0.051 (device_cond) и 0.071-0.078 (pipe_cond)
   при n=5000, для MLE и Bayesian estimation почти идентично (ожидаемо —
   при n=5000 BDeu-приор почти не влияет).
6. Warning: `MaximumLikelihoodEstimator`/`BayesianEstimator` из
   `pgmpy.estimators` **тоже** deprecated (аналогично StructureScore) в
   пользу `pgmpy.parameter_estimator.DiscreteMLE`/`DiscreteBayesianEstimator`.
   Работает, но при обновлении pgmpy в будущем может потребовать той же
   фолбэк-логики импорта, что и `BayesianNetwork`.

**Вывод для будущих правок:** пользователь на очень новой версии pgmpy, где
API активно переименовывается (минимум 3 независимых deprecation-варнинга подряд).
Любой новый pgmpy-код лучше сразу писать с try/except на оба варианта имени
(старое/новое), и после каждого добавления — просить пользователя прогнать
и прислать вывод, а не считать код рабочим до подтверждения.

## 6. Оценка проекта на текущий момент (что сильно / что слабо)

**Сильные стороны:**
- Реальный, количественно доказанный бизнес-эффект пилота — редкость для
  junior-заявок, ровно то, что JMLC прямо просит показать.
- Explaining away не просто описан, а протестирован
  (`test_explaining_away_reduces_leak_probability`).
- Две независимые реализации (numpy-перебор и pgmpy), обязанные совпадать —
  настоящая инженерная практика взаимной проверки.
- Честность в README про происхождение чисел (что точно из диплома, что
  реконструировано) — редкость, работает в плюс на серьёзной комиссии.
- Обучение параметров теперь реально показано с числами, а не только
  задекларировано.

**Слабые места / ещё не закрыто:**
- Обучение структуры (HillClimbSearch vs экспертный граф) — не сделано,
  следующий по значимости пункт для критерия "выбор моделей".
- Разрыв в `CPT_FAILURE` для сценария 3 Табл. 3.6 (0.37 vs 0.70 у диплома)
  не откалиброван — задокументирован в README и тестах (`TOLERANCE`), но
  не устранён по существу.
- macro-F1 в `baselines.py` скачет немонотонно из-за дисбаланса классов —
  не объяснено, если спросят на питчинге.
- Ноутбуки не сделаны, только заглушка-план в `notebooks/README.md`.
- Презентации/питч-дека для JMLC вообще нет — отдельная задача, никак не
  начата.
- pgmpy версия не закреплена (см. п.5).

**Приоритет следующих шагов (по убыванию отдачи на время):**
1. Закрепить версию pgmpy в requirements.txt (быстро, снимает риск поломки CI)
2. Обучение структуры (HillClimbSearch) — осторожно с deprecated BicScore/StructureScore
3. Презентация/питч-дек для JMLC
4. Калибровка `CPT_FAILURE`, сценарий 3
5. Ноутбуки (можно последними, весь код уже есть в `src/`, ноутбуки — просто витрина)
