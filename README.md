# Байесовская сеть доверия для предиктивного ТО инженерных систем

Python-реализация системы поддержки принятия решений (DSS) на основе
байесовской сети, оригинально разработанной и защищённой как выпускная
квалификационная работа: Поповцев Н.О., «Разработка системы управления
качеством технического обслуживания инженерных систем с использованием
байесовских сетей доверия», СПбГЭУ, 2026 (научный руководитель — к.т.н.,
доцент Л.В. Виноградов).

**Зачем этот репозиторий, если модель уже защищена и работает в HUGIN
Researcher?** Диплом решал задачу управления качеством и был выполнен по
заданию, зафиксировавшему HUGIN как среду реализации. Этот репозиторий —
самостоятельное продолжение той же научной работы: та же сеть, тот же
причинно-следственный граф, но выраженная в виде воспроизводимого,
тестируемого Python-кода, с решающим слоем, анализом чувствительности,
восстановлением структуры по данным и открытым сравнением с ML-подходами.

### Главный результат: решение зависит не от порога, а от цены ошибки

![Компромисс между ложными выездами и пропусками](reports/figures/decision_tradeoff.png)

Слева: каждая точка синей кривой — своя цена пропущенного отказа. Оба
альтернативных правила лежат **выше** кривой, то есть доминируются: при том
же числе ложных выездов байесовская политика пропускает меньше аварий.
Справа: при одинаковом бюджете выездов ранжирование по ожидаемой выгоде
продолжает снижать пропуски там, где пороговое правило упирается в потолок.

## Бизнес-контекст (из диплома)

ООО «Спецмастер» — микропредприятие в Республике Коми, обслуживающее
приборы учёта тепла и воды. Реактивная модель обслуживания («выезд по
жалобе или по превышению порога расхода») давала много ложных выездов и
пропущенные отказы. В ходе производственной практики была развёрнута АИС
на базе ЛЭРС УЧЁТ (32 объекта, ежесуточный опрос, 97.8% успешных сессий),
а поверх неё — аналитический слой на байесовской сети, переводящий
показания приборов в вероятностные оценки риска и рекомендации.

**Результаты пилота (реальные, из диплома, не из этого репозитория):**

| Показатель                    | До      | После        |
| ----------------------------- | ------- | ------------ |
| Ложные выезды, в месяц        | 6–8     | 1–2 (↓ ~75%) |
| Пропущенные отказы, в квартал | 3       | ≤ 1          |
| Время реакции на аномалию     | 24–72 ч | 2–6 ч        |

Как эти числа корректно формулировать: это наблюдения «до/после» без
контрольной группы, на 32 объектах за два месяца, частично ретроспективно
(часть параметров уточнялась на тех же данных, на которых проверялась
модель). Поэтому корректно говорить «после внедрения ложные выезды
снизились с 6–8 до 1–2 в месяц», а не «модель снизила ложные выезды на
75%»: дизайн не позволяет отделить вклад модели от вклада самой АИС и от
эффекта наблюдения. Для строгой оценки нужна проспективная апробация на
полном отопительном сезоне — это и написано в самом дипломе.

## Архитектура сети

Трёхуровневая иерархия «данные → скрытые состояния → управленческие
гипотезы» (см. `src/network_spec.py` — единственный источник истины по
структуре и CPT):

```
Вход (АИС)                Скрытые состояния            Выход (решения)
──────────────            ──────────────────           ────────────────────
давление      ──┬────────→ состояние прибора ──┬─────→ вероятность отказа ─┐
температура   ──┤     ┌──→ состояние трубопр. ─┼──┬──→ необходимость ТО ←──┘
расход        ──┴─────┤                        │  │
срок поверки  ────────┼──→ достоверность ──────┴──┴──→ аномальное потребл.
срок эксплуат.────────┘         показаний
```

Точный список из 20 дуг — в `PARENTS` (`src/network_spec.py`); схема выше
передаёт уровни, а не каждую дугу. 11 узлов, 2–3 состояния каждый,
428 свободных параметров (полное пространство ≈ 79 000 комбинаций — для
точного вывода перебором это тривиально; HUGIN в оригинале использует
алгоритм дерева сочленений, см. §3.1 диплома).

### Пересмотр структуры (расхождение с §3.2)

Изначально репозиторий воспроизводил структуру §3.2 буквально, и у неё был
измеримый дефект: узел `temperature` объявлен входом в Табл. 3.2, но
причинных дуг от него текст не описывает, поэтому в графе он висел ни с чем
не связанный. `python -m src.sensitivity` показывал размах отклика 0.0000 по
всем трём выходам и ценность информации ровно 0 — то есть канал АИС
опрашивался впустую.

Структура пересмотрена по результатам опроса эксперта предприятия. Было 13
дуг, стало 20: добавлены восемь (давление и температура → состояние прибора;
температура → состояние трубопровода; поверка, срок эксплуатации и состояние
трубопровода → достоверность показаний; состояние прибора и достоверность →
необходимость ТО), дуга `device_cond → reliability` снята, а `failure_prob`
получил третьего родителя (`flow`) по итогам калибровки. Дуга `flow → anomaly` — единственная,
перепрыгивающая через промежуточный уровень, — по итогам разбора сохранена,
но ослаблена вдвое; почему именно так, разобрано ниже.

**Норма температуры — не абсолютная величина.** Она задаётся температурным
графиком: по усреднённой за 12–24 ч уличной температуре берётся положенная
температура теплоносителя, допуск ±3 % (ПТЭ тепловых энергоустановок, приказ
Минэнерго России от 24.03.2003 № 115). Это проценты, а не градусы: на 70 °C
допуск ≈ ±2.1 °C, на 130 °C ≈ ±3.9 °C. Признак `temperature` на входе должен
считаться именно так, иначе узел получает шум вместо сигнала.

**Что дал пересмотр.** Согласие с Табл. 3.6 по девяти числам: RMSE
0.138 → **0.047**, расхождений за пределами допуска 3 → 0, максимальное
отклонение 0.075. Оговорка о том, что часть этого согласия куплена
подгонкой, — ниже, в разделе о калибровке; она существенная, и читать
таблицу без неё нельзя. Температура перестала быть мёртвым
узлом: размах отклика 0.1998, взаимная информация 0.0120 бит, ценность
информации 0.0025 у.е. на объект — эффект слабый, но ненулевой, и это
согласуется с экспертной трактовкой (отклонение от графика чаще означает
ошибку теплоснабжающей организации, чем отказ прибора).

**Чего пересмотр структуры не дал.** Расхождение в сценарии 3 (0.37 против
0.70) не изменилось от новых дуг ни на сотую: в сценарии 3 давление и
температура в норме, поэтому на `failure_prob` они не влияют вообще.
Гипотеза о недостающем родителе пережила пересмотр нетронутой — и в итоге
была принята отдельным решением, см. «Гипотеза B принята» ниже.

**Почему `flow → anomaly` пришлось сохранить.** Дугу сначала удалили: она
единственная перепрыгивала через промежуточный уровень, а диплом прямо
критикует пороговые правила по расходу (§3.1). Удаление немедленно
улучшило сценарий 3 (0.31 → 0.18 при 0.18 в дипломе) и сломало сценарий 1
(0.74 → 0.51 при 0.67). Причина оказалась арифметической, а не
настроечной. В сценарии 1 строка Табл. 3.4 — точные числа диплома — даёт
P(нарушена герметичность) = 0.75, поэтому при родителях
{`pipe_cond`, `reliability`} потолок равен

```
0.15·0.07 + 0.75·0.85 + 0.10·0.05 = 0.653
```

и достигается он только при идеально достоверных показаниях. Дипломные
0.67 недостижимы **при любых** значениях остальных CPT. Значит, в исходной
сети HUGIN у аномального потребления был вход помимо трубопровода.

Дуга возвращена с половинной силой (`FLOW_WEIGHT = 0.5` в
`network_spec.py`). Коэффициент выбран до подбора — «вдвое слабее», — а не
найден сканированием: подгонка одного параметра под три числа
недоопределена ровно в том смысле, за который этот README критикует
калибровку без штрафа за искажение. Для честности вот вся кривая, а не
только выбранная точка:

| `FLOW_WEIGHT` | сц. 1 (диплом 0.67) | сц. 3 (диплом 0.18) |
| ------------- | ------------------- | ------------------- |
| 0.0 (дуги нет) | 0.51 | 0.18 |
| **0.5** | **0.57** | **0.22** |
| 1.0 (как было) | 0.62 | 0.25 |

Оба крайних варианта хуже середины: без дуги проваливается сценарий 1, при
полной силе расход поднимает тревогу там, где диплом её гасит. Отдельно
стоит отметить, что даже при полной силе сценарий 1 даёт лишь 0.62 —
остаток расхождения даёт не расход, а новая дуга `pipe_cond → reliability`
(см. ниже, «Спорный момент»).

**Снятая дуга `pipe_cond → reliability`.** В первой версии пересмотра она
была: эксперт сказал, что нарушенная герметичность сильно влияет на
достоверность показаний. Дуга оказалась вредной, причём не по числам, а по
смыслу. `reliability` — потомок `pipe_cond` и одновременно родитель
`anomaly`, поэтому чем сильнее свидетельство за разгерметизацию, тем выше
получалась P(недостоверная), а та через «объяснение прочь» гасила вывод об
утечке. Сеть тем меньше верила в утечку, чем больше было улик за утечку: в
сценарии 1 она оценивала P(недостоверная) = 0.53 и сама себе сбивала
тревогу.

Повторный опрос показал расхождение в терминах. Узел означает «прибор
исправно измеряет», а эксперт отвечал про «показания отражают реальное
потребление» — при утечке прибор меряет верно, просто мерить ему нечего.
Второе — это и есть `anomaly`, то есть потомок гидравлики, а не её
соучастник. Дуга снята, `reliability` вернулась к трём родителям (расход,
поверка, срок эксплуатации), сценарий 1 по аномалии поднялся с 0.57 до
0.60 без единой правки чисел.

Полезный побочный вывод: расхождение такого рода не ловится проверкой
согласия с Табл. 3.6 — оно ловится вопросом «а что этот узел вообще
означает». Формулировки состояний стоит согласовывать с экспертом до
опроса о вероятностях, а не после.

**Цена пересмотра.** Свободных параметров стало 428 вместо 146, и это
ухудшило обучаемость: раньше CPT, оценённые по 20 наблюдениям, обгоняли
экспертные, теперь — только начиная примерно с 1000 (см. раздел о
baselines). Табл. 3.3 и Табл. 3.4 при этом сохранены бит-в-бит: новые
родители внесены моделью пропорциональных шансов, в которой «новый родитель
в норме» возвращает ровно строку из диплома.

## Что здесь есть

### 1. Решающий слой — `src/decision.py`

Сеть выдаёт вероятности, но решение «ехать или нет» — это вероятность
**плюс цена ошибки**. Правило Табл. 3.5 (`действие = argmax вероятности`)
неявно предполагает, что пропустить аварию так же плохо, как съездить
зря. Здесь асимметрия сделана явной: `a*(e) = argmin_a Σ_s P(s|e)·L(a,s)`.

Синтетический прогон, на 100 объектов:

| стратегия                          | ложных срочных выездов | пропущено срочных случаев |
| ---------------------------------- | ---------------------- | ------------------------- |
| реактивное правило (порог расхода) | 5.3                    | 10.2                      |
| БСД + argmax (Табл. 3.5)           | 0.7                    | 11.5                      |
| БСД + мин. ожидаемых потерь (R=5)  | 4.3                    | **2.2**                   |

Отдельного внимания стоит средняя строка: правило Табл. 3.5 в лоб
пропускает **больше** срочных случаев, чем даже грубый порог по расходу.
Оно экономит выезды за счёт пропусков, и без матрицы потерь это не видно.

Порог перестаёт быть магической константой: `breakeven_ratio()` показывает,
что для сценария 1 Табл. 3.6 срочный выезд окупается начиная с R ≈ 2.5,
где R — во сколько раз пропущенный отказ дороже выезда. Это та ручка,
которую руководитель предприятия может крутить осознанно.

Плюс `triage()` — ранжирование заявок, когда бригада одна и физически
может сделать только K выездов: реальная задача диспетчера не «ехать или
нет», а «на какие объекты ехать в первую очередь».

### 2. Чувствительность и ценность информации — `src/sensitivity.py`

Три сценария Табл. 3.6 покрывают 3 комбинации входов из 108 и молчат об
остальных 105. Здесь систематическая проверка: торнадо-диаграмма размаха
отклика, взаимная информация вход→выход в битах и ценность информации
(VOI) в единицах ожидаемых потерь — то есть «какой канал АИС стоит своих
денег». Самый ценный вход — давление (0.031 у.е. на объект сверх
остальных четырёх), самые слабые — срок поверки (0.004) и температура
(0.006). До пересмотра структуры температура давала ровно 0, и именно
этот модуль сделал проблему измеримой, а не декларативной.

### 3. Восстановление структуры по данным — `src/structure_learning.py`

Жадный поиск по BIC, чистый numpy (о том, почему не pgmpy, — ниже).
F1 по скелету графа растёт с 0.46 при n=200 до 0.74 при n=5000 и 0.78 при
n=20000.

Это заметно хуже, чем было до пересмотра структуры (0.63 → 0.86), и хуже
ожидаемо: граф стал плотнее (20 дуг вместо 13), а часть новых дуг слабые
по построению. Температура сдвигает распределения на единицы процентов,
поэтому её дуги требуют на порядок больше наблюдений, чем дуги давления.
Падение F1 здесь — не регресс алгоритма, а честное следствие того, что
восстанавливать стало нечего сильного: слабую причинную связь по
наблюдательным данным видно плохо, и это ровно тот случай, когда
экспертный граф даёт то, чего данные такого объёма дать не могут.

Направленная F1 при этом остаётся низкой, и это не дефект алгоритма: по
наблюдательным данным структура восстановима лишь с точностью до класса
Маркова-эквивалентности — направление дуги, не входящей ни в одну
v-структуру, принципиально неразличимо. Поэтому основная метрика здесь —
скелет, а направленная приводится справочно.

### 4. Калибровка `CPT_FAILURE` и структурная гипотеза — `src/calibration.py`

Реконструированная сеть воспроизводила Табл. 3.6 качественно, но в
сценарии 3 давала P(отказ = высокая) = 0.37 против 0.70 в дипломе.

Разбор чисел диплома: в сценариях 2 и 3 состояние прибора одинаково, а
P(отказ) отличается вдвое (0.52 против 0.70); при этом в сценарии 3
трубопровод *вероятнее* исправен. Значит, разницу нельзя объяснить через
`pipe_cond` — у `failure_prob` есть родитель, которого нет в текстовом
описании структуры §3.2. Проверяются три гипотезы о наборе родителей,
для каждой CPT подбирается минимизацией
`Σ(p_модель − p_диплом)² + λ·||logit − logit_эксперт||²`.

```
                      было     стало
сценарий 3, P(отказ)  0.37     0.64    (диплом 0.70)
RMSE по 6 числам      0.139    0.042
```

Что здесь важно не переоценить: при λ = 0 под шесть чисел подстраивается
**любая** гипотеза, включая исходную структуру, — шесть уравнений против
27–81 параметра, задача недоопределена, и «удалось подогнать» само по себе
ничего не доказывает. Содержательна только *цена* подгонки. После
пересмотра структуры гипотезы разошлись отчётливо (λ = 0.05):

| гипотеза: родители `failure_prob` | RMSE к диплому | среднее искажение |
| --------------------------------- | -------------- | ----------------- |
| A: device, pipe (как в §3.2)      | 0.062          | 0.124             |
| **B: device, pipe, flow**         | **0.042**      | **0.046**         |
| C: device, pipe, reliability      | 0.059          | 0.104             |

Гипотеза B доминирует по обеим осям сразу: лучше согласие и вдвое-втрое
меньше искажение экспертной таблицы
(`reports/figures/calibration_pareto.png`). До пересмотра структуры B и C
шли вплотную и различить их было нельзя; расхождение появилось после того,
как `reliability` перестала зависеть от `device_cond` и `pipe_cond`.

**Гипотеза B принята.** `failure_prob` получил третьего родителя (`flow`), и
подогнанная таблица подставлена в `network_spec.py` как действующая. Прежняя
двухродительская реконструкция сохранена рядом под именем
`CPT_FAILURE_EXPERT` — она нужна калибровке как точка отсчёта для штрафа за
искажение.

**Чем за это заплачено, прямым текстом.** Согласие со сценарием 3 по узлу
`failure_prob` теперь **тавтологично**: таблица подогнана под те самые
шесть чисел, с которыми её потом сверяет `scripts/verify_reference.py`. Для
`failure_prob` этот скрипт перестал быть независимой проверкой и годится
только как регрессионный тест — поймать случайную порчу таблицы. Для
`maintenance` и `anomaly` проверка осталась осмысленной: их CPT не
подгонялись, а Табл. 3.6 они воспроизводят в пределах 0.075.

Что при этом НЕ куплено подгонкой и остаётся содержательным: во-первых,
сравнение гипотез между собой — цена подгонки считается при одинаковом λ и
одинаковом числе уравнений, поэтому доминирование B информативно;
во-вторых, поведение таблицы там, где сценарии молчат. Все девять строк с
`flow = "anomal_low"` совпали с экспертной реконструкцией до четвёртого
знака: низкого расхода нет ни в одном сценарии Табл. 3.6, штраф λ удержал
эти строки на месте, и подгонка не расползлась по всей таблице. Если бы
расползлась — это был бы признак, что она ловит шум, а не структуру.

Окончательно вопрос закрывается не оптимизацией, а выгрузкой из АИС с
зафиксированными исходами отказов.

### 5. Сравнение с ML-моделями — `src/baselines.py`

Первая версия этого сравнения была некорректной, и это стоит сказать
прямо: данные порождались той же сетью, чьё качество измерялось, поэтому
БСД была байесовски-оптимальной **по построению**, а её «точность» 0.686
— не характеристика модели, а байесовский предел задачи.

Исправлено: два режима (данные из экспертной сети и из **возмущённой**
сети, где структура верна, а параметры — нет), метрики — правила скоринга
(log-loss, Brier) вместо accuracy, добавлены логистическая регрессия и
БСД с CPT, обученными по данным.

Log-loss в осмысленном режиме (данные из возмущённой сети, меньше — лучше):

| n\_train | DecisionTree | RandomForest | LogisticReg | GradBoosting | БСД экспертная | БСД обученная | предел |
| -------- | ------------ | ------------ | ----------- | ------------ | -------------- | ------------- | ------ |
| 20       | 13.60        | 3.53         | 1.16        | 0.99         | 0.882          | 0.997         | 0.871  |
| 100      | 5.33         | 2.37         | 0.94        | 0.95         | 0.882          | 0.914         | 0.871  |
| 1000     | 1.29         | 1.22         | 0.89        | 0.91         | 0.882          | **0.873**     | 0.871  |
| 10000    | 0.93         | 0.90         | 0.88        | 0.88         | 0.882          | **0.870**     | 0.871  |

**Этот вывод пересмотр структуры ослабил, и это надо сказать прямо.** До
пересмотра БСД с CPT по 20 наблюдениям уже обгоняла экспертную версию.
Теперь для этого нужно около 1000 наблюдений: параметров стало 428 вместо
146, и оценивать их не из чего. При 20 наблюдениях обученная БСД (0.997)
проигрывает экспертной (0.882) — данных не хватает даже на структуру,
которая их резко экономит.

Что уцелело: экспертный **граф** по-прежнему бьёт модели без структуры на
всём диапазоне. Логистическая регрессия догоняет предел только к n = 1000,
деревьям и бустингу нужны тысячи наблюдений, а БСД выходит на предел
раньше всех. То есть исходное утверждение «выигрыш даёт граф, а не
экспертные вероятности» держится — но цена более богатой структуры видна
именно здесь, и на малых выборках экспертные CPT остаются лучшим, что есть.

## Структура репозитория

```
├── src/
│   ├── network_spec.py         # структура + CPT -- единственный источник истины
│   ├── model.py                # обобщённый движок БС (тензорные CPT, вывод, обучение)
│   ├── reference_inference.py  # независимый оракул: точный вывод перебором, только numpy
│   ├── network.py              # pgmpy-модель (вторая независимая реализация)
│   ├── decision.py             # решающий слой: матрица потерь, политики, triage
│   ├── sensitivity.py          # торнадо, взаимная информация, VOI
│   ├── calibration.py          # подгонка CPT_FAILURE, проверка структурной гипотезы
│   ├── structure_learning.py   # жадный поиск по BIC (numpy, без pgmpy)
│   ├── learning.py             # обучение параметров через pgmpy (MLE / Bayesian)
│   ├── data_generator.py       # синтетика методом ancestral sampling
│   ├── baselines.py            # сравнение с ML-моделями, два режима
│   └── visualization.py        # граф сети
├── notebooks/
│   ├── 0*.ipynb                # собранные ноутбуки с выводами и графиками
│   └── sources/*.py            # повествование как код, отсюда они собираются
├── scripts/
│   ├── verify_reference.py     # CLI-проверка против Табл. 3.6
│   ├── build_notebooks.py      # сборка + выполнение ноутбуков без jupyter
│   └── eda_report.py           # распределения + причинные кросс-табы
├── tests/
│   ├── test_reference.py       # без pgmpy -- работает всегда
│   ├── test_new_modules.py     # 30 тестов: движок, решения, VOI, калибровка, структура
│   ├── test_network_pgmpy.py   # требует pgmpy
│   └── test_learning.py        # требует pgmpy
├── app/streamlit_app.py        # интерактивная демонстрация с решающим слоем
└── requirements.txt / Dockerfile / .github/workflows/ci.yml
```

**Три независимые реализации вывода.** `reference_inference.py` (перебор
по захардкоженным CPT), `model.py` (обобщённый тензорный движок) и
`network.py` (pgmpy) обязаны давать одинаковые ответы. Тест
`test_engine_matches_reference_oracle` сверяет первые две на всех 108
комбинациях входных свидетельств с точностью 1e-12; `test_network_pgmpy.py`
подключает третью. Это не избыточность, а взаимная проверка: ошибка в CPT
или в структуре ломает совпадение раньше, чем доедет до выводов.

**Почему `structure_learning.py` не на pgmpy.** В свежих версиях pgmpy API
активно переименовывается (`BayesianNetwork` → `DiscreteBayesianNetwork`,
`MaximumLikelihoodEstimator` → `DiscreteMLE`, `StructureScore` →
`structure_score`). Эксперимент, который должен воспроизводиться через год,
на такой фундамент ставить не хочется. BIC для дискретной сети раскладывается
по узлам и укладывается в сотню строк numpy — это надёжнее и полностью под
контролем. pgmpy при этом остаётся в проекте как независимая проверка.

## Запуск

```bash
pip install -r requirements.txt

# тесты (ядро проекта не требует pgmpy)
pytest -v

# проверка против диплома
python -m scripts.verify_reference

# решающий слой: сравнение стратегий, ограниченная бригада, разбор решения
python -m src.decision

# чувствительность, взаимная информация, ценность информации
python -m src.sensitivity

# калибровка CPT_FAILURE и проверка структурной гипотезы
python -m src.calibration

# восстановление структуры по данным
python -m src.structure_learning

# сравнение с ML-моделями (два режима, log-loss)
python -m src.baselines

# синтетические данные / обучение параметров через pgmpy / граф и EDA
python -m src.data_generator --n 5000
python -m src.learning
python -m src.visualization
python -m scripts.eda_report

# пересобрать ноутбуки после правки notebooks/sources/*.py
python -m scripts.build_notebooks

# интерактивная демонстрация
streamlit run app/streamlit_app.py

# либо всё в контейнере
docker build -t bsd-maintenance . && docker run -p 8501:8501 bsd-maintenance
```
