# Байесовская сеть доверия для предиктивного ТО инженерных систем

Python-реализация системы поддержки принятия решений (DSS) на основе
байесовской сети, оригинально разработанной и защищённой как выпускная
квалификационная работа: Поповцев Н.О., «Разработка системы управления
качеством технического обслуживания инженерных систем с использованием
байесовских сетей доверия», СПбГЭУ, 2026 (научный руководитель — к.т.н.,
доцент Л.В. Виноградов).

**Зачем этот репозиторий, если модель уже защищена и работает в HUGIN
Researcher?** Диплом решал задачу управления качеством и был выполнен по
заданию, зафиксировавшему HUGIN как среду реализации. Этот репозиторий —
самостоятельное продолжение той же научной работы: та же сеть, тот же
причинно-следственный граф, но выраженная в виде воспроизводимого,
тестируемого Python-кода, с открытым сравнением с альтернативными
ML-подходами и интерактивной демонстрацией.

## Бизнес-контекст (из диплома)

ООО «Спецмастер» — микропредприятие в Республике Коми, обслуживающее
приборы учёта тепла и воды. Реактивная модель обслуживания («выезд по
жалобе или по превышению порога расхода») давала много ложных выездов и
пропущенные отказы. В ходе производственной практики была развёрнута АИС
на базе ЛЭРС УЧЁТ (32 объекта, ежесуточный опрос, 97.8% успешных сессий),
а поверх неё — аналитический слой на байесовской сети, переводящий
показания приборов в вероятностные оценки риска и рекомендации.

**Результаты пилота (реальные, из диплома, не из этого репозитория):**

| Показатель | До | После |
|---|---|---|
| Ложные выезды, в месяц | 6–8 | 1–2 (↓ ~75%) |
| Пропущенные отказы, в квартал | 3 | ≤ 1 |
| Время реакции на аномалию | 24–72 ч | 2–6 ч |

Ограничение, о котором диплом сам честно пишет: пилот — 32 объекта, 2
месяца, ретроспективный прогон (часть параметров уточнялась на тех же
данных, на которых проверялась модель) → нужна проспективная апробация
на полном сезоне для строгой оценки точности.

## Архитектура сети

Трёхуровневая иерархия «данные → скрытые состояния → управленческие
гипотезы» (см. `src/network_spec.py` — единственный источник истины по
структуре и CPT):

```
Вход (АИС)          Скрытые состояния        Выход (решения)
─────────────       ──────────────────       ─────────────────
давление      ─┐                        ┌─→ вероятность отказа
температура    │                        │
расход        ─┼─→ состояние прибора ────┼─→ необходимость ТО
срок поверки   │   состояние трубопровода│
срок эксплуат.─┘   достоверность показаний┴─→ аномальное потребление
```

11 узлов, 2–3 состояния каждый (полное пространство ≈ 79 000 комбинаций —
для точного вывода перебором это тривиально; HUGIN в оригинале использует
алгоритм дерева сочленений, см. §3.1 диплома).

## Происхождение чисел (важно для честности перед экспертами)

| Что | Статус |
|---|---|
| Структура сети (какой узел от какого зависит) | Из текста §3.2 диплома |
| CPT `device_cond` (техническое состояние прибора) | **Точно** Табл. 3.3 |
| CPT `pipe_cond` (состояние трубопровода) | **Точно** Табл. 3.4 |
| CPT `reliability`, `failure_prob`, `maintenance`, `anomaly` | Реконструированы: согласованы с качественной логикой §3.2, приблизительно валидированы по сценариям Табл. 3.6 |
| Априорные вероятности входных узлов | Допущение для симуляции, не из диплома |
| Реальные данные пилота (32 объекта) | Не публикуются (собственность ООО «Спецмастер»); везде далее — синтетика |

Полные CPT из исходного файла HUGIN (`.net`) в тексте диплома не
приведены (там даны только показанные выше фрагменты), поэтому четыре
CPT из шести — это моя реконструкция, а не копия оригинала. Она проверена
скриптом `scripts/verify_reference.py` на трёх диагностических сценариях
из Табл. 3.6:

```
Сценарий 1 (утечка, средний возраст прибора)
  failure_prob  P(высокая)=0.37   диплом=0.42   Δ=-0.05
  maintenance   P(срочное)=0.49   диплом=0.58   Δ=-0.09
  anomaly       P(утечка)=0.74    диплом=0.67   Δ=+0.07

Сценарий 2 (старый прибор, засор/насос, без роста расхода)
  failure_prob  P(высокая)=0.38   диплом=0.52   Δ=-0.14
  maintenance   P(срочное)=0.34   диплом=0.40   Δ=-0.06
  anomaly       P(утечка)=0.16    диплом=0.09   Δ=+0.07

Сценарий 3 (фильтрация ложной тревоги — explaining away)
  failure_prob  P(высокая)=0.37   диплом=0.70   Δ=-0.33  ← известный разрыв, см. ниже
  maintenance   P(срочное)=0.30   диплом=0.35   Δ=-0.05
  anomaly       P(утечка)=0.31    диплом=0.18   Δ=+0.13
```

Направление и качественные эффекты (усиление риска при совпадении
симптомов, «объяснение прочь» при недостоверных показаниях) воспроизведены
верно во всех трёх сценариях. Абсолютные числа для `failure_prob` в
сценарии 3 расходятся заметнее (0.37 vs 0.70) — похоже, что в оригинальной
сети у `failure_prob` есть дополнительная прямая связь с возрастом/сроком
поверки помимо опосредования через `device_cond`, которой нет в текстовом
описании структуры. Это главный пункт калибровки на неделю (см. дорожную
карту).

## Запуск

```bash
pip install -r requirements.txt

# тесты (без pgmpy сработает подмножество -- test_reference.py)
pytest -v

# проверка против диплома
python -m scripts.verify_reference

# синтетические данные
python -m src.data_generator --n 5000

# сравнение с ML-моделями (см. честную оговорку в src/baselines.py!)
python -m src.baselines

# обучение параметров (MLE / Bayesian estimation) vs экспертные CPT
python -m src.learning

# граф сети и мини-EDA (рисунки -> reports/figures/)
python -m src.visualization
python -m scripts.eda_report

# интерактивная демонстрация
streamlit run app/streamlit_app.py

# либо всё в контейнере
docker build -t bsd-maintenance . && docker run -p 8501:8501 bsd-maintenance
```

## Сравнение с ML-моделями: что это показывает и что не показывает

`src/baselines.py` обучает Decision Tree / Random Forest / Gradient
Boosting на синтетических данных разного объёма (20…3000 наблюдений) и
сравнивает точность с БСД (у которой CPT заданы экспертно и не требуют
обучения). **Данные сгенерированы из этой же сети**, поэтому это не
нейтральное сравнение «в вакууме» — БСД тут почти по определению
близка к байесовски-оптимальной. Ценность демонстрации — в форме кривой:

| n_train | DecisionTree | RandomForest | БСД (эталон) |
|---|---|---|---|
| 20 | 0.606 | 0.631 | 0.686 |
| 100 | 0.655 | 0.650 | 0.686 |
| 1000 | 0.680 | 0.678 | 0.686 |
| 3000 | 0.686 | 0.683 | 0.686 |

Деревья и лес нужно тренировать почти на порядок больше наблюдений, чтобы
догнать точность, которую БСД получает бесплатно из экспертных CPT — это
именно тот содержательный аргумент из §3.1 диплома (малые размеченные
выборки, типичные для инженерной диагностики), просто проверенный
эмпирически, а не только описанный качественно.
